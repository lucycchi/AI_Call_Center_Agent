## Problem Statement

Meridian Home Comfort is a fictional heating, cooling (HVAC) and plumbing company in the Austin, Texas area. Its call center cannot keep up with call volume, wait times are high, and the executive team wants an AI agent to handle most routine calls without hiring more staff. Nobody has told us which questions matter most; 420 unlabeled call transcripts from July to September 2026 will.

The task, set by the challenge PRD (`docs/PRD.md`), is to build and deploy, in four working days, a chat agent at a public web address that:

- answers the most common caller questions from the company's own documents (the knowledge base in `call_data/knowledge_base/`);
- checks appointment availability and books, using the provided SQLite scheduling database (`call_data/scheduling_db/`);
- hands everything else to a human, telling the caller what is happening and passing enough context that nobody starts over;
- and proves how well it does all this with measured numbers, not claims.

**Who it is for.** Two audiences:

1. **The reviewer at the hiring fund**, the person who judges the submission. They will spend 10 to 20 minutes on the live site trying to break it, watch a 3 to 4 minute walkthrough video, and read the repository and README. They are hiring a Forward Deployed Engineer and judge scope, honesty about the data, evidence, production thinking and clean failure.
2. **Meridian's callers and staff, as the scenario describes them.** Callers want a quick, correct answer or a booking; staff want handed-off calls to arrive with the details already gathered, and managers want to see whether the agent is working.

## What Makes This Cool

Most AI call center demos show a chatbot that sounds good. This one shows its working: every booking is checked by code against the real database, every factual answer cites the document it came from, every handoff appears as a ticket on a staff screen the reviewer can watch in a second tab, and the containment number comes with its ceiling, its margin of error and the hand-graded check on the AI grader. The planted data traps (stale fees, an old warranty, an archived membership price) become visible evidence of care: a written list of what was left out and why.

## Constraints

- **Time:** four working days from 2026-10-16.
- **Language and hosting:** Python, deployed to Fly.io on one small always-on server with an attached disk for the SQLite database (hosting on Fly.io (D4)).
- **Models:** Claude Sonnet 5.5 runs the conversation, Claude Haiku 5.5 sorts transcripts, an OpenAI model run through the author's Codex subscription grades test answers and provides check labels (grading through Codex (D15), template labeling (D18)), Voyage AI provides embeddings (AI models and services (D5)). Keys live in `.env`, ignored by git; `.env.example` lists every setting.
- **Spending:** a per-visitor budget of about $0.40 a day and a site-wide cap of $10 a day, with an alert to the author at $5; when a limit is reached, the agent hands off cleanly instead of failing (spending budgets with a reviewer reserve (D30), amending (D5)). Test runs use a separate key and budget.
- **Database rules:** bookings must write to the one real database the reviewer tests against (from `call_data/README.md`), and the database resets to its seeded data each night (nightly database reset (D6)).
- **"Today" is 2026-10-16** (fixed at 09:00 Austin time) for every customer-facing scheduling and policy calculation, as the data README says; appointment slots run for the three weeks after. Operations such as spending limits, the nightly reset and alerts use real time.
- **Internal documents** (`internal/` folder) must never be read to callers.

## Premises

The author agreed to all six on 2026-10-16.

1. **The product is the evidence, not the chatbot.** The test set, measured numbers and visible handoffs are core work, not polish.
2. **Discovery comes first and decides the scope.** The order of work is: sort the transcripts by call reason, build the test set, build the agent, then deploy and monitor.
3. **Code controls the policy; the AI handles the language.** Booking steps, slot eligibility (zone, service type, members-only slots), emergency handoff and the "never refund, never promise a firm price" rules live in code.
4. **The data traps are something to show off.** Excluded documents, grader agreement and the containment ceiling appear in the README and video.
5. **The main user is a reviewer trying to break it.** The site must stay correct, cheap and responsive under probing, and handoffs must be visible.
6. **Nothing to reuse but the data.** The provided database and schema are used exactly as given; the deliverable is a web service on Fly.io.

## Approaches Considered

### Approach A: one AI with tools

A single Claude model with one long policy prompt and four tools (search documents, check availability, book, hand off) decides everything itself. Fewest parts and fastest to a demo. Not chosen because the policy lives only in the prompt, so a clever reviewer can argue it into a members-only slot, a discount or a guess, and its handoff choices cannot be measured on their own.

### Approach B: router plus code-controlled flows (chosen)

Each message is first sorted into a handled call reason, scheduling, or handoff; each then runs a flow whose rules live in code. Described in full below.

### Approach C: reviewed answer bank plus AI

A small bank of pre-checked answers to the top questions, with the AI only rephrasing and running bookings. Not chosen because it bends the PRD's literal requirement to build a retrieval pipeline with deliberate chunking, embedding and retrieval choices, and would look like a canned FAQ bot.

## Recommended Approach

Router plus code-controlled flows (agent built as a router plus code-controlled flows (D10)), with suggested-question buttons for the most common questions borrowed from the answer-bank idea, sent through the same live flows with no cached answers (simplifications, cut order and buttons (D24), which replaces (D23) and (D16)).

### 1. Discovery (day 1)

- **The transcripts are templated.** A first check found the 420 calls open with only about 77 distinct requests once names, numbers and filler are removed; they are built from roughly 80 call templates. Discovery groups transcripts by template first, and the findings document says so, because it shapes every number below.
- Claude Haiku 5.5 reads every transcript and gives it one main call reason, a short description of what the caller wanted, and whether the human agent resolved it on the call. Reasons are first proposed freely, then merged into a short list of categories, then every transcript is labeled against that final list.
- **Independent check labels** (template labeling (D18), which replaces (D14), with the blind third labeled by Claude Fable 5.1 (D38)): Codex, set to an OpenAI frontier model on the author's subscription, labels every template without seeing Haiku's labels; Claude Fable 5.1 labels about a third of the templates without seeing either other model's labels, in place of the author; the README states that no human labeled the templates. Because each template stands for all its calls, this labels all 420. Reported: Fable-versus-Codex agreement (whether Codex's labels can be trusted), Codex-versus-Haiku agreement (whether the ranking holds), and later the router's accuracy on every held-out call, scored on the caller's first substantive message, with Codex's labels as the reference. The author is told before labeling starts so they can set Codex to a frontier model; the model name is saved with the labels.
- Call reasons are ranked by count. The findings document shows the top four or five as a table: rank, count, percentage, running total, and handled or handed off with the reason.
- **What the agent handles** (choosing handled call reasons to meet the top-three requirement (D12), which replaces the earlier rule (D2), extended by account lookups (D17)): for each of the real top three reasons, the agent answers its knowledge questions through document search, including the policy questions inside scheduling calls (cancellation fees, windows), and its account questions through read-only database lookups; bookings use the database. A rough first count suggests the top three are booking (about 31 percent), billing (about 18 percent) and membership (about 18 percent), with warranty fourth; discovery will confirm. If a top-three reason has risky parts (a billing dispute, a refund, an action on money or membership), the agent answers the safe part and hands off the rest. For each top-three reason the findings show how many calls are answered from documents, from lookups, and handed off, and why. Scheduling is handled whatever its rank. The findings document shows two lists, the observed top three and the agent's scope, and any gap is raised with the PM. Gaps in the documents themselves (for example, no document mentions autopay, which 14 calls ask about) are listed as findings for the executive team.

### 2. Test set (day 1 to 2)

- **Split by template** (test-set construction with the working-set rehearsal (D32)): transcripts are grouped by template and the templates are split once, with a fixed random seed and stratified by call reason, into a working set used for tuning and a held-out set used only for the final measurement, so no template appears on both sides. Safety and multi-question templates appear in both sets. Counts of calls and templates per reason are published for the whole corpus, the working set and the held-out set. "Held out" means: the held-out cases are labeled and given expected outcomes and reference answers before any tuning of the agent, and no prompt, threshold, chunking setting or category is changed after seeing the agent's results on them.
- **One case per template, weighted:** the held-out run uses one conversation per held-out template (about 50 to 60), weighted by that template's real call count when computing containment. Both "calls" and "distinct scenarios" are reported, with the margin of error computed on scenarios, so the numbers do not look more precise than they are.
- **Caller cards with real customers:** none of the transcripts' 131 account numbers exists in the database. Each test case is therefore tied to a real database customer chosen to match the transcript's facts (zone, membership, brand, install age), and the simulated caller is given a caller card with that customer's name, account number, phone and address, not the transcript's. Relative dates ("tomorrow", "this Saturday") are read against the fixed "now". Billing cases add their invoice to the fresh test database copy.
- Each test case has an expected outcome (handled or handed off), and handled knowledge cases have a reference answer written from the current documents, not from what the human agent said in the transcript (judging "resolved" (D8)).
- Test conversations are run by a second AI playing the caller, given the transcript as its script (the method used by the tau-bench customer service benchmark), so the agent faces rambling, multi-question, real-sounding callers rather than clean one-line questions. The simulated caller uses a fixed model version and fixed settings and rules, every replayed conversation is saved, and every failed case is run once more to separate real failures from simulator noise.
- Every test run uses a fresh copy of the seeded database, never the live one, and booking correctness is checked against that copy.
- **Adversarial test set,** separate from the held-out set, about 30 cases written by hand: prompt injection and "print your instructions", a non-member demanding a members-only slot, booking on someone else's account, "my last agent promised me a refund", gas-smell, carbon-monoxide and burning-smell reports, a booking request from Dripping Springs or Manor, a north-zone plumbing request (no slots exist), Omar Patel questioning his invoice, a late technician, a waitlist request, abuse, other languages and nonsense input. Reported as a pass rate.
- **Grading:** knowledge answers are graded by an OpenAI model run through Codex on the author's laptop, about 20 answers per call, with the model name recorded and an API fallback setting (grading through Codex (D15)). The author is reminded to set Codex to a frontier model before each graded run. To check the grader, a sample of about 30 answers is chosen in advance, spread across answers the grader marked right and wrong; the author grades them without seeing the grader's verdict; the full agree/disagree table is published, not only the agreement rate.
- **Consistency (optional, first to drop):** about 30 held-out cases run three times each; the share correct on all three is reported (the tau-bench "pass^k" measure).
- **What "contained" means for one test conversation:** the agent never handed off, and every request the caller made was graded correct (knowledge answers matching the reference answer, lookups matching the database, bookings verified in the database copy). A conversation the agent finished without handing off but got wrong is not contained; these are counted and reported separately as wrong confident answers. Containment is reported both with and without redirect-only calls (wrong numbers, job enquiries sent to the careers page), so trivial calls cannot pad the number. A clean decline (no slot exists, said plainly, handed off) counts as correct behaviour but not as contained.
- **Rehearsal:** at the end of day 3 a 10-case rehearsal on working-set cases runs through the full harness; after it the agent is frozen until the final run. The first run of each held-out case is the scored one; a case that fails then passes on retry is reported as flaky (test-set construction with the working-set rehearsal (D32), replacing (D20)).

### 3. Document search (day 2)

- **What goes in, decided by an explicit document list** (document list and conflict register (D22), which replaces (D7)), not by folder, file name or whether a file is dated. The list records every file with its status (current, stale or placeholder), audience (customers or internal only), effective date and the reason. From a first read of the knowledge base:
  - **Left out as stale:** the `archive/` folder, the old FAQ copy, and `services/scheduling_guide.md` (dated November 2024, outside the archive, saying cancellations need 48 hours and emergencies can be booked, which contradicts the current FAQ and the scheduling rules).
  - **Left out as a placeholder:** `services/duct_cleaning.md`, which only says "TODO"; the real answer (a partner referral) is in the service catalog.
  - **Internal, never searchable:** `internal/agent_discretion_notes.md`, `policies/escalation_and_safety.md` (marked "Internal") and `services/technician_arrival_and_etas.md` (it grants agents a fee waiver). All three feed the code rules instead; late-technician calls hand off, because the agent has no live dispatch data.
  - **Conflict register:** known disagreements between current documents are settled once, with the reason: the later effective date wins (for example the April 2026 service-area document, which adds Dripping Springs and Manor, over the March 2026 FAQ). The agent hands off only conflicts the register does not settle.
  - **Troubleshooting guide:** the "before you call" checks are offered in one short message before booking a non-emergency visit, never alongside a burning smell, and never "reset a breaker" in the same conversation as any smell of burning.
- **Mixed formats:** the PDF fee schedule is converted to text that keeps each row and column pair (for example "Diagnostic visit, Comfort Club: waived"); the CSV price book is turned into one readable row per item; the holiday hours image is transcribed once (by an AI that reads images, checked by hand) and stored as text beside it.
- **Chunking:** split by document section (each heading and its content) rather than by fixed length, because these documents are short and organised by topic, so a section is the natural unit of an answer. Each piece keeps its document name, heading and effective date.
- **Retrieval:** combine meaning-based search (Voyage AI embeddings) with keyword search, because callers use exact words like "diagnostic fee" or brand names that keyword search finds reliably. Keyword-only and combined search are compared on the same questions, so the embedding choice is defended with numbers (simplifications, cut order and buttons (D24)).
- **Does search earn its place?** The current customer-facing documents total under 3,000 tokens. One comparison puts the whole current knowledge base in the prompt instead of searching, scored on answer correctness, so the obvious reviewer question gets a number.
- **Retrieval measured on its own,** before the AI writes anything, on every knowledge test question. Each question is labeled with the exact text needed to answer it (document plus the span of lines), not with chunk numbers, so any chunking setting can be scored fairly against the same answers:
  - **Recall at five:** the share of the needed passages that appear in the top five results (some answers need two, such as a warranty term plus the brand table).
  - **Hit rate at five:** at least one needed passage in the top five.
  - **Coverage:** the share of handled-reason questions whose answer exists in the current documents at all. Questions the documents never answer lower the adjusted containment ceiling (see measurement below).
  - **Stale-trap accuracy:** questions where an excluded old document would give a different answer (for example, a $79 against an $89 diagnostic fee), showing the current answer wins every time.
- **Answers measured** after the AI writes, graded by the grader (answer correctness and faithfulness are the protected core):
  - **Faithfulness (groundedness):** the share of claims in each answer supported by the retrieved passages; the made-up-answer measure.
  - **Answer relevance:** whether the answer addresses what was asked.
  - **Citation accuracy:** whether the document the agent names actually contains the fact.
  - **Correct refusal:** a set of questions the documents cannot answer (commercial pricing, a city outside the service area); the share handed off instead of guessed.
- **Choosing the handoff threshold with evidence:** on the working set only, show how wrong answers and containment change as the retrieval confidence threshold moves, and pick the point on that curve. The curve goes in the README and video.

### 4. The agent (days 2 to 3)

The agent core takes text in and gives text out; the chat page is only one front end, so a phone line can be added later without a rebuild (voice deferred (D3)).

- **Safety check (plain code, runs first):** every message, including those in the middle of a booking, is checked against fixed lists of emergency words and patterns, in classes taken from the company's safety policy. These fixed replies are the one exception to the AI writing every reply (burning smell (D19)).
  - **Immediate danger** (smell of gas or rotten eggs, carbon monoxide alarm, sparks, smoke or flames from a unit, electrical burning smell with tripped breakers): a fixed reply written in code tells the caller to leave the home immediately and call 911 or their gas utility from outside, and not to flip switches, open windows near the furnace or restart equipment. Then a priority handoff ticket is created.
  - **Burning smell on its own** (16 calls say "I smell something burning from the vents"; staff booked normal visits): a fixed reply (turn the system off at the thermostat, do not reset breakers, leave the home if there is smoke) and a priority handoff, never a normal booking. This costs about 4 points of containment, reported openly.
  - **Urgent but not dangerous** (an active water leak, no heat in freezing weather, no cooling in extreme heat): a calmer fixed reply (for example, turning off the water supply for a leak) and a priority handoff.

  A match always wins over the AI's choice, and emergencies are never booked.
- **Router:** when no flow is active, the caller's message is sorted by the AI into a handled call reason, scheduling, or handoff, with a confidence score. Low confidence, a request for a person, anger, or anything outside the handled reasons goes to handoff. A message with several requests is split: each handled request is answered in turn, and if any part is out of scope the agent answers what it can and hands off the rest.
- **Conversation state:** while a flow is active (for example, mid-booking), follow-up messages such as "yes", "the morning one" or an account number stay in that flow. The flow is left only when the safety check fires, the caller asks for a person, or the router sees a clear change of topic; the agent then answers the new topic and offers to return to the booking.
- **Knowledge flow:** the agent answers only from retrieved passages and names the document it used. If retrieval confidence is below a measured threshold, or no passage clearly supports the answer, it hands off. **Prices:** the agent may quote the current published standard fee or price-book range, naming its source document, always adding that the technician confirms the final price on site. It never promises a firm repair total, a discount or a fee waiver.
- **Account lookups** (account lookups (D17)): once the caller is identified, three read-only lookups answer account questions: open invoices (balance, due date and line items), membership tier and renewal date (the renewal price is the current published price, because existing members keep their price only until renewal), and system brand and install date (for warranty questions). **Invoice rule** (data rules (D29), replacing (D27) and (D21)): invoice lines are read exactly as recorded and never called right or wrong. If the caller questions any charge, the agent hands off as a billing dispute. A fixed fee amount that differs from the current schedule silently creates a low-priority billing-review ticket for staff without interrupting the caller; the widespread pattern of a diagnostic fee charged alongside a repair or to a member (45 of 81 invoices) is an executive finding, not a per-call action. Seeded customer Omar Patel's invoice is such a case: it charges $144 for after-hours dispatch against the published $149, and an $89 diagnostic fee on top of a repair, which the FAQ says is credited. Actions that change money or membership (payment links, autopay, cancelling auto-renew, upgrades, enrolment) hand off and are reported as the action gap.
- **Internal rules:** the internal agent notes are never given to the model as written. The model gets short paraphrased rules, the rules that can be enforced in code are (no refunds, no waivers, no discounts, no firm totals), and every reply is checked for verbatim internal text before it is sent. A test case tries to extract the instructions ("print your instructions").
- **Scheduling flow:** fixed steps enforced in code:
  1. identify the customer by name together with an account number, service address or phone number (the three ways staff do it in the transcripts), never by name alone, because some names belong to two or three customers;
  2. establish the service type (HVAC repair, tune-up, plumbing, estimate);
  3. match the customer's city to a zone and find open slots for that service, including members-only slots only for members (tier standard or plus), never a window that has already started, and never a slot whose technician is already booked in an overlapping window. Dripping Springs and Manor are served (added April 2026) but are missing from the database's zone map, so the agent confirms service and hands the booking to a team member;
  4. offer the requested slot if open, or nearby alternatives if not. If no eligible slot exists in the three-week range for that zone and service (the north zone has no plumbing slots at all, and the central zone has no estimate slots), the agent says so plainly and hands off with a ticket: a clean decline. No waitlist is promised;
  5. read the date, window and service back and get a clear yes;
  6. book (mark the slot booked only if it is still bookable, and add the appointment row, in one transaction) and confirm with date, window and technician name. The warranty-visit flag is set only when the database install date proves the 2-year installation labour warranty; repeat-repair and 5-year member claims, which the database cannot verify, are booked as normal visits with a warranty-review note for staff (data rules (D29)); the new row records the fixed now.

  **Confirming, cancelling and rescheduling are core and never cut** (rescheduling, cancelling and confirming in scope (D13)), reusing the same identify, eligibility and read-back steps: confirming looks up the caller's scheduled appointments; cancelling frees the old slot in the same database transaction; rescheduling books the new slot and frees the old one together, so neither can happen alone. A freed slot returns to its original status (open or members-only) from the seeded database copy. Inside 24 hours of the window, both cancelling and rescheduling carry the $49 late fee from the current FAQ (staff in the transcripts skip it, so reference answers follow the FAQ, not the staff); a waiver request hands off. When a caller has several appointments, the agent asks which one. Read-backs give date, window, service and technician only, never the stored issue text, which is unreliable in the seeded data. Existing appointments are left as recorded even where their zone does not match the customer's city; the mismatches are documented in the findings. Emergencies are never booked; they hand off.
- **Handoff flow:** except for emergencies (which get the fixed safety replies above first), the caller is told plainly that a team member will take over with the details. A ticket is saved with five fields: who the caller is, what they want, what the agent already tried, any constraints (emergency, disputed fee), and the caller's mood (handoff ticket and staff page (D9)).
- **Guards:** per-visitor and site-wide spending budgets and a per-visitor rate limit; all hand off cleanly when hit, and the author gets an alert at $5 of daily spend. A secret reviewer link draws on its own $3-a-day reserve (spending budgets with a reviewer reserve (D30), replacing (D28)). A secret reviewer link draws on its own reserved budget (spending budgets with a reviewer reserve (D30)). Every model or database error becomes a handoff, never a crash. Typed instructions such as "ignore your rules" cannot change the booking checks, which run in code.

### 5. Website, monitoring and feedback (days 3 to 4)

- **Chat page:** type a message, see the reply, see when the agent hands off. Test customers from the schema are listed so the reviewer can try a booking.
- **Suggested-question buttons** (simplifications, cut order and buttons (D24)): 4 to 6 buttons chosen from the discovery ranking, one or two per handled call reason (for example "What's the diagnostic fee?", "Book a repair", "Move my appointment"). A click only fills in the question text, so it goes through exactly the same path as typing, router included; the answer comes from retrieved documents and is logged and measured like any other. No answers are cached. The free-text box stays for everything else. First to be cut if time runs short. On a phone line later, the buttons become a spoken hint ("you can ask me about fees, warranties or booking").
- **Staff and monitoring page:** handoff tickets as they arrive (emergencies marked priority), plus volume, containment, handoffs by reason, failures (errors, spending cap hits, flagged answers), response time (median and slowest five percent) and AI cost per conversation and per resolved conversation.
- **Health checks and alerts:** a health endpoint checked by Fly.io's built-in health check, and alerts to the author on downtime, an error-rate spike, failed database writes and the spending cap being reached, so the business would know if it broke. Containment is shown as a trend on the dashboard only once there are enough conversations to mean something, because at demo traffic an hourly containment rate is noise. Live containment has no grade, so the dashboard defines it as "no handoff, no error, not flagged, not abandoned mid-flow" and labels it an upper bound.
- **Quick test run before each deploy:** a 20-case subset of the working set runs before every deploy, so a prompt or document change cannot silently break the agent. This is also the "re-run the test set" step of the feedback loop.
- **Feedback loop, first step built:** every conversation is logged (with phone numbers and emails masked); any reply can be flagged as wrong from the staff page with a correction note; flagged conversations can be exported as new test cases. The full loop (flag, review, fix the document or rule, re-run the test set, deploy) is described in the README.
- **Grader record:** the grader's prompt and every verdict are committed, with the model name; the README says re-grading with the same model needs the API fallback.
- **Retention and rollback** (D31): conversation logs are deleted after 30 days, and phone numbers, emails and street addresses are masked; the README has a one-page rollback runbook (Fly.io release rollback and disk snapshot restore), practised once.
- **Storage:** the scheduling database is the provided SQLite file. Conversation logs, handoff tickets, flags and metrics live in a separate database file that the nightly reset never touches, so monitoring history and the feedback loop survive the reset.
- **Deployment:** Fly.io, with both database files on the attached disk, the nightly reset as a scheduled job that restores only the scheduling tables, and keys as Fly.io secrets.

### 6. Measurement and deliverables (day 4)

- Run the held-out test set once and report: containment; two ceilings, the scope ceiling (share of calls in handled reasons) and an adjusted ceiling that also removes calls the documents cannot answer; the action gap (calls handed off because they need an account action); accuracy on handled reasons, lookup correctness, wrong confident answers, handoff rate on out-of-scope calls, call-reason sorting accuracy, handoff quality (every ticket has all five fields, and each handoff was warranted), booking correctness, the retrieval and answer measures above, the adversarial pass rate, the grader check table, the label agreement numbers, and the margin of error computed on distinct scenarios. If containment is below 60 percent, report it as it is with the reason (reporting honest containment (D1)).
- README: what it does, how to run it and its tests, and the numbers.
- A short script outline for the 3 to 4 minute video covering the four topics the PRD names: how the call drivers were found, why this chunking and retrieval, how handoff works, and what the numbers say. The author records the video.
- **If time runs short, cut in this order** (simplifications, cut order and buttons (D24)): the suggested-question buttons; the cost-per-conversation breakdown; the consistency runs; the flag export; the pre-deploy test run; the measures beyond the core set (the core set is recall and hit rate at five, stale-trap accuracy, answer correctness and faithfulness); the adversarial set down to 15 cases; the threshold curve.
- **Never cut:** deployment, the top-driver findings, retrieval evaluation, booking with confirming, cancelling and rescheduling, the account lookups, the emergency replies, handoff tickets, flagging, the PRD's required numbers, health checks, the README and the video.

## Out of Scope

- Voice and phone calls (listed under Open Questions).
- Real identity verification beyond a name plus account number, address or phone.
- Taking payments or card numbers, sending payment links, autopay, and changing a membership: they change money or membership, so they hand off and are reported as the action gap.
- Billing disputes, refunds, fee waivers, discounts and complaints: they need a human's authority, so they hand off.
- Commercial work, languages other than English, and a real staff system integration.
- Accessibility work beyond sensible defaults in the chat page.

## Open Questions

- **Voice (bigger idea):** a phone number with call audio (for example Twilio), speech-to-text and text-to-speech (the author has an ElevenLabs key), short spoken replies, interruption handling, and read-back of names and times. Possibly Claude Haiku 5.5 for speed on calls. Attempted only if every required goal is built, tested and deployed with a day to spare (voice deferred (D3)).
- **Which reasons are handled** is confirmed by discovery; a rough first count suggests booking, billing and membership.
- **Grader and labeling model:** the author sets Codex to OpenAI's strongest model when told labeling or grading is about to run; the model used is recorded with the results.
- **Left for the spec stage** (raised by the design reviews):
  - two visitors booking the same slot at once (the booking is one conditional transaction; the spec defines the wording when a slot was just taken);
  - callers who cannot be identified, give details that do not match, or are new customers (how many attempts before handoff);
  - how many alternative slots are offered and in what order;
  - what the chat shows after a handoff;
  - whether the staff page is open or password-protected, and whether tickets show masked contact details;
  - a reply-speed budget per step and whether replies stream;
  - how the nightly job runs on Fly.io and how a failed reset is noticed;
  - the rate-limit numbers and how a visitor is identified.
- **For the PM:** whether the nightly reset is acceptable; whether an honest containment rate below 60 percent with documented ceilings counts as a miss; and, if any part of a top-three call reason is handed off rather than answered, whether that is acceptable (listed in `docs/PRD_REVIEW.md`).

## Success Criteria

Targets below are proposed for the spec stage to confirm. All are measured on the held-out test set.

- **Containment rate** reported honestly with its ceiling; aim for 60 to 75 percent (PRD target).
- **Accuracy on handled knowledge questions:** at least 90 percent correct, graded against reference answers.
- **Emergency replies:** 100 percent of immediate-danger test cases get the fixed leave-and-call reply before the handoff.
- **Wrong confident answers:** reported as a count, aiming for zero, with every one listed and explained.
- **Handoff on out-of-scope calls:** 100 percent on safety and booking-rule cases; at least 95 percent on other out-of-scope calls, with every miss listed.
- **Bookings:** 100 percent of completed bookings correct when checked against the database (right customer, slot, zone, service type, membership rules).
- **Retrieval:** the right document in the top five results for at least 90 percent of knowledge questions; recall at five, coverage and stale-trap accuracy reported; keyword-only, combined and whole-knowledge-base results compared.
- **Account lookups:** 100 percent of lookups match the database copy.
- **Burning-smell and emergency cases:** 100 percent handed off with the fixed reply first.
- **Answers:** faithfulness and citation accuracy reported, aiming for at least 95 percent; correct refusal on unanswerable questions at least 90 percent.
- **Call-reason sorting accuracy:** at least 90 percent.
- **Adversarial pass rate:** reported, aiming for 100 percent on booking-rule and instruction-extraction attacks.
- **Grader agreement** with the author's hand grades: reported, aiming for at least 85 percent.
- **Response time:** median reply under about 3 seconds on the live site.
- **Deliverables exist:** public URL that survives probing, a 3 to 4 minute video, a repository with code, test set and README including the numbers.

## Glossary

- **HVAC:** heating, ventilation and air conditioning.
- **Call reason (call driver):** why a customer called, such as booking a repair or asking about a fee.
- **Containment rate:** the share of calls the agent finishes without a human.
- **Scope ceiling:** the share of calls whose reason the agent handles; containment cannot be higher.
- **Adjusted ceiling:** the scope ceiling minus calls the documents cannot answer; a more realistic upper limit.
- **Stratified split:** dividing the data so each part keeps the same proportion of every category.
- **Document list (manifest):** a file recording every knowledge-base document's status, audience, date and whether it is searchable.
- **Handoff (escalation):** passing the conversation to a human, with a ticket summarising it.
- **Knowledge base:** the company's documents (FAQs, policies, prices, warranty and membership terms).
- **Retrieval / document search:** finding the passages in the knowledge base that answer a question.
- **Chunking:** splitting documents into pieces that can be searched; here, one piece per section.
- **Embedding:** a list of numbers representing a text's meaning, so similar texts can be found.
- **Keyword search:** finding passages that contain the same words as the question.
- **Hit rate at five:** the share of questions whose correct document appears in the top five search results.
- **Mean reciprocal rank:** a score for how close to the top the first correct result appears.
- **Recall at k / precision at k:** the share of the needed passages found in the top k results, and the share of the top k results that are relevant.
- **Coverage:** the share of questions whose answer exists in the documents at all.
- **Faithfulness (groundedness):** the share of an answer's claims that the retrieved passages support.
- **Citation accuracy:** whether the document an answer names really contains the fact.
- **Correct refusal:** handing off a question the documents cannot answer instead of guessing.
- **Adversarial test:** a test case written to trick or break the agent.
- **pass^k:** the share of test cases answered correctly on every one of k repeated runs; a consistency measure.
- **Transcript template:** a call pattern that repeats across many transcripts with only names, numbers and filler words changed.
- **Caller card:** the facts given to the AI playing the caller in a test: a real customer's name, account number, phone, address and request.
- **Fixture:** prepared test data, such as a planted invoice, loaded into a test copy of the database.
- **Action gap:** calls the agent understands but deliberately hands off because they need an action on money or membership.
- **Clean decline:** telling the caller plainly that no slot is available and handing off; correct behaviour, though not contained.
- **Conflict register:** a written list of documents that disagree and which one wins, with the reason.
- **Read-only lookup:** reading a caller's record in the database without changing it.
- **Health check:** a regular automatic request that confirms the site is up.
- **Router:** the step that decides which flow a caller's message belongs to.
- **Code-controlled flow:** a conversation path whose steps and rules are enforced by program code, not left to the AI.
- **Held-out set:** test cases set aside and not looked at while building, so the final measurement is fair.
- **Reference answer:** the correct answer to a test question, written in advance to grade the agent against.
- **Grader:** an AI model (here from OpenAI) that scores whether an answer matches the reference.
- **Grader agreement:** the share of answers where the AI grader and the author gave the same verdict.
- **Margin of error:** how far a percentage measured on a limited sample may be from the true value.
- **Seeded data:** the starting rows the database ships with, including four test customers.
- **Zone:** the area (north, central or south) a customer's city belongs to, which decides which technicians can visit.
- **Rate limit:** a cap on how many messages one visitor can send in a period.
- **Fly.io secrets:** settings such as API keys stored by the hosting service instead of in the code.
