AI Call Center Agent

Current stage: Milestone gate, milestone 3 of 6 (needs your approval before moving on)

Summary

The problem. Meridian Home Comfort, a fictional heating, cooling and plumbing company in the Austin area, cannot keep up with its calls. The challenge (docs/PRD.md) is to build, in four working days, a chat agent at a public web address that answers routine calls from the company's documents, reads callers' accounts, books and changes appointments in a provided SQLite database, hands everything else to a human with full context, and proves its performance with numbers measured on held-out data.

The approach. One Python web application on one always-on Fly.io machine. Every caller message passes through a fixed pipeline: a safety check written in code, a fast AI router (Claude Haiku 5.5) that picks a flow, and a flow whose rules are enforced in code (knowledge answers from document search, read-only account lookups, booking changes in database transactions, and handoff tickets). Claude Sonnet 5.5 only writes the wording of replies, and every sentence is checked in code before it reaches the screen. A separate operations database records every conversation, ticket, cost and error, feeds the staff view and alerts, and is never touched by the nightly reset of the scheduling data. Offline tools, run on the author's laptop, sort the transcripts, build the search index, run the simulated-caller test set and grade answers through Codex.

Where the project stands. The intent (docs/DESIGN.md), the specification (docs/SPEC.md, 86 numbered requirements), this architecture and the plan (docs/PLAN.md) are approved, with the decisions recorded in docs/DECISIONS.md; the technology stack is its own decision (technology stack (D35)). Milestones 1 to 3 of 6 are built: configuration and the agent-core interface, transcript templates and labels, the findings document (docs/FINDINGS.md) and the prepared documents; then section-based keyword and meaning search, the frozen working and held-out test cases, and the standalone retrieval results; then the agent core: identification and account lookups, slot eligibility and booking transactions, the safety check, the operations store, the knowledge, account, scheduling and handoff flows, the router and the engine pipeline, with a terminal chat (python -m app.cli). Specification: AI Call Center Agent for Meridian Home Comfort

Status: approved · Date: 2026-10-17 · Builds on: the approved design (docs/DESIGN.md) and the decision log (docs/DECISIONS.md).

1. Purpose and context

Meridian Home Comfort is a fictional heating, cooling and plumbing company in the Austin, Texas area whose call center cannot keep up with calls. This project builds, in four working days, a chat agent at a public web address that answers routine calls, books and changes appointments in the company's scheduling database, reads callers' own account details, hands everything else to a human with full context, and proves its performance with measured numbers. It is a take-home challenge (docs/PRD.md) judged by a reviewer at a private equity fund hiring a Forward Deployed Engineer. The reviewer will spend 10 to 20 minutes trying to break the live site, watch a 3 to 4 minute walkthrough video, and read the repository.

The data is in call_data/: 420 unlabeled call transcripts from July to September 2026, a 17-file knowledge base (some files stale, some internal, some contradictory), and a SQLite scheduling database with customers, technicians, appointment slots, appointments and invoices, documented in call_data/scheduling_db/SCHEMA.md. A first data review (docs/DATA_REVIEW.md) found the top three call reasons are new bookings (31 percent of calls), billing (18 percent) and Comfort Club membership (18 percent), by both call count and staff minutes; that staff resolve 85 percent of calls on the first call (about 73 percent excluding account actions the agent will not take); that staff make a policy error in 26 percent of calls; and that appointment capacity is badly misallocated between zones.

Goals. Contain as many calls as is safe, never give a confident wrong answer, hand off cleanly with context, and back every claim with a number measured on held-out data.

Non-goals. Voice and phone calls (deferred unless every required item is finished with a day to spare); taking payments or changing money or membership; real identity verification; commercial work; languages other than English; integration with a real staff system.

Anti-goals (it would count as a failure even if it "works"): a containment number inflated by loose grading, leaked test data or trivial calls; booking an emergency; quoting a stale price; reading internal notes to a caller; a reviewer seeing another visitor's conversation; the demo breaking because the calendar or the budget was used up.

2. Fixed facts the whole system uses

  • "Now" for customer-facing scheduling and policy rules is one setting: 2026-10-16 09:00, Austin (US Central) time, a Friday. Every booking, fee-window, warranty and "has this window started" calculation uses it, never the server clock. Operations (spending and rate limits, the nightly reset, alerts and reply timing) use real time. Slots run from 2026-10-16 to 2026-11-05.
  • Zones: north is Round Rock, Cedar Park, Pflugerville, Georgetown, Leander and Hutto; central is Austin; south is Kyle and Buda. Dripping Springs and Manor are served (added April 2026) but have no zone in the database.
  • Appointment windows: 08:00–12:00, 12:00–16:00, 13:00–17:00, and 16:00–19:00 on Tuesdays and Thursdays only.
  • Service types: HVAC repair, HVAC tune-up, plumbing, and estimate (a free in-home replacement estimate).
  • Slot statuses: open (bookable), booked, reserved for members (bookable only by Comfort Club standard or Plus members), blocked.
  • Current fees (2026 fee schedule): diagnostic visit $89, credited toward a repair approved on the same visit and waived for members; after-hours dispatch $149, waived for members; holiday dispatch $199; late cancellation or reschedule inside 24 hours $49; tune-up $129 for non-members; members get 15 percent off repairs, Plus members also 15 percent off plumbing; membership $189 a year or $16.99 a month, $99 per extra system; Plus $269 a year.
  • Models: Claude Haiku 5.5 (model ID claude-haiku-5-5) sorts transcripts and routes messages (routing model (D25)); Claude Sonnet 5.5 (claude-sonnet-5-5) writes replies and plays the simulated caller; the model IDs, SDK version and request settings are pinned in configuration and logged with every run; an OpenAI frontier model run through the author's Codex subscription labels templates and grades answers (template labeling (D18), grading through Codex (D15)); Voyage AI provides embeddings (AI models and services (D5)).

3.0 Scope: what the agent handles

  • R81: The agent handles, hands off, or answers and redirects calls as follows (handled-reason list (D26)). Handled: new bookings, including replacement estimates; confirming, rescheduling and cancelling appointments; billing questions answered from documents or lookups (current balance, what an invoice is for, and being charged twice, which gets the FAQ's pending-authorisation explanation first and is handed off only if the caller says both charges posted); membership questions (what it includes, price, renewal date); warranty questions and claims (coverage, registration, transfer, and booking a warranty or repeat-repair visit with the warranty-visit flag). Handed off: quote disputes and refunds; complaints and manager requests; late technicians (no live dispatch data); every action on money or membership (the action gap); safety emergencies, after the fixed safety reply; commercial work. Answered and redirected: hiring enquiries (to the careers page) and wrong numbers, reported with and without them.

3.4 Agent core

  • R33: The agent core takes text in and gives text out with a conversation identifier, independent of the web page, so another front end such as a phone line could use it later (voice deferred (D3)).
  • R82: A visitor's browser may hold several conversations, one per open tab; each conversation has its own identifier, is stored in the operations database so it survives a restart, and closes after 30 minutes without a message or when the caller ends it. (Builder's call.)
  • R34: Before anything else, every caller message, including those in the middle of a flow, is checked in code against fixed lists of words and patterns in three safety classes; a match always overrides the router. The safety check normalises case, punctuation, common misspellings and speech-to-text errors and handles plain negations ("I don't smell gas" does not trigger); when unsure it errs toward safety.
  • R35: Immediate danger (smell of gas or rotten eggs, carbon monoxide alarm, sparks, smoke or flames from a unit, electrical burning smell with tripped breakers) gets a fixed reply written in code: leave the home immediately and call 911 or the gas utility from outside, and do not flip switches, open windows near the furnace or restart equipment; then a priority handoff ticket.
  • R36: A burning smell on its own gets a fixed reply (turn the system off at the thermostat, do not reset breakers, leave the home if there is smoke) and a priority handoff, never a normal booking; advice to reset a breaker is never given in a conversation that mentions a burning smell (burning smell (D19)).
  • R37: Urgent but not dangerous situations (an active water leak, no heat in freezing weather, no cooling in extreme heat) get a calmer fixed reply (for example turning off the water supply for a leak) and a priority handoff. Emergencies are never booked.
  • R38: When no flow is active, Claude Haiku 5.5 sorts the caller's message into a handled call reason, scheduling, an account question or a handoff, returning a route and a label of "clear" or "unclear" (routing model (D25)); the rule for "unclear" is tuned on the working set. A request for a person, anger or abuse, an unclear route, or anything outside the handled reasons goes to a handoff.
  • R39: A message with several requests is split; each handled request is answered in turn, and if any part is out of scope the agent answers what it can and hands off the rest in one ticket.
  • R40: While a flow is active, follow-up messages ("yes", "the morning one", an account number) stay in that flow; the flow is left only when the safety check fires, the caller asks for a person, or the router returns a clear different route, after which the agent answers the new topic and offers to return.
  • R41: Knowledge answers come only from retrieved passages and name the source document. If retrieval is below the chosen threshold or no passage clearly supports the answer, the agent hands off.
  • R42: The agent may quote the current published fee or price-book range with its source, always adding that the technician confirms the final price on site; it never promises a firm repair total, a discount beyond the published member discounts, a refund or a fee waiver. Replies are produced in structured reply types and checked in code; a sentence that fails a check is replaced by a handoff, and every block is logged and counted so false positives are visible.
  • R43: The model is never given internal documents as written, only short paraphrased rules; every reply is checked in code, across the whole reply so far, for any run of 8 or more consecutive words matching an internal document after normalising case and punctuation, and a match is replaced by a handoff. An adversarial test tries to extract the instructions.
  • R44: The agent never promises a waitlist; it offers the next eligible slots or a handoff ticket marked "wants an earlier slot".
  • R45: The agent identifies a caller by name together with an account number, service address or phone number, never by name alone. After two failed attempts it hands off; a caller not in the database (a new customer) is handed off to be set up.
  • R46: Once a caller is identified, the agent answers three kinds of account question with read-only database lookups: open invoices (balance, due date and line items, read exactly as recorded), membership tier and renewal date (the renewal price is the current published price), and system brand and install date (account lookups (D17)).
  • R47: Invoice lines are read exactly as recorded and never called right or wrong. If the caller questions any charge, the agent hands off as a billing dispute. If a fixed fee amount on the invoice (diagnostic, after-hours, holiday, late cancellation) differs from the current schedule, for example Omar Patel's $144 after-hours line against $149, the agent silently creates a low-priority billing-review ticket for staff without interrupting the caller. A diagnostic fee charged alongside a repair or to a member is not acted on per call; the pattern goes in the findings document (data rules (D29)).
  • R48: Requests to take an action on money or membership (payment links, autopay, cancelling auto-renew, upgrades, enrolment, refunds, fee waivers) are handed off and tagged as the action gap.
  • R49: To book, the agent establishes the service type, matches the customer's city to a zone, and finds slots that are open (or reserved for members, if the customer's tier is standard or Plus), match the zone and service type, have not started relative to "now", and whose technician is not already booked in an overlapping window.
  • R50: If the requested slot is eligible the agent offers it; otherwise it offers up to three eligible slots, nearest to the requested date first, then by window from morning to evening, naming overlapping windows (12:00–16:00 and 13:00–17:00) distinctly.
  • R51: If no eligible slot exists in the three-week range for that zone and service, the agent says so plainly and hands off with a ticket naming the gap (a clean decline). Callers in Dripping Springs or Manor are told the area is served and handed off for booking.
  • R52: Before writing, the agent reads back the date, window and service type and waits for a clear yes; the booking then marks the slot booked and adds the appointment row in one database transaction that succeeds only if the slot is still bookable. If it was just taken, the agent says so and offers the next three slots.
  • R53: A new appointment records the fixed "now" as its creation time. The warranty-visit flag is set only when the database install date proves the 2-year installation labour warranty applies. Repeat-repair claims and 5-year member-installation claims, which the database cannot verify, are booked as normal visits with a low-priority warranty-review ticket for staff linked to the appointment, and the caller is told there is no diagnostic fee if the technician confirms coverage (data rules (D29)).
  • R54: The agent confirms a caller's scheduled appointments, reading back only date, window, service type and technician, never the stored issue text; if the caller has several, it asks which one (rescheduling, cancelling and confirming in scope (D13)).
  • R55: Cancelling frees the slot and marks the appointment cancelled in one transaction; rescheduling books the new slot and frees the old one in one transaction. A freed slot returns to its status in the seeded database copy if that was open or members-only; if the seed copy itself shows the slot as booked (a seeded appointment), it is freed to open, as the schema says (freed-slot fallback (D33)). Inside 24 hours of the window's start, both state the $49 late fee before the caller confirms; a waiver request hands off.
  • R56: Existing appointments are left as recorded even where their zone does not match the customer's city; the mismatches are listed in the findings document.
  • R57: Every handoff creates a ticket with five fields (who the caller is, what they want, what the agent already tried, constraints such as an emergency or a disputed fee, and the caller's mood), a reason tag, a priority flag for emergencies, and a ticket number (handoff ticket and staff page (D9)). In testing, ticket quality is graded with a rubric: a staff member could act without asking the caller to repeat anything.
  • R58: After a handoff, the chat stays open and shows the ticket number and a plain statement that the team will contact the caller within one business day (or that an emergency was flagged); the caller may keep asking other questions, and later messages in the conversation are added to the open ticket; nothing implies a person will reply live.
  • R59: Every model, search or scheduling-database error becomes a handoff with a plain message, never a crash or an error page. If the operations database itself is unavailable, so no ticket can be saved, the caller sees a plain message asking them to phone the office, and the failure is written to the server log and raises an alert.
  • R60: Replies are shown sentence by sentence: each sentence is released to the screen only after it passes the fee, refund and internal-text checks (R42, R43), so unchecked text never appears. Glossary

  • Call reason (call driver): why a customer called, such as booking a repair or asking about a bill.
  • Template: a call pattern that repeats across many transcripts with only names, numbers and filler words changed.
  • Containment: the share of calls the agent finishes correctly without a human.
  • Scope ceiling / adjusted ceiling: the highest containment possible given the agent's scope, and that ceiling after removing calls the data cannot answer or that need account actions.
  • Action gap: calls handed off because they need an action on money or membership.
  • Clean decline: telling the caller plainly that no slot is available and handing off; correct, but not contained.
  • Human baseline: the share of calls staff resolved on the first call.
  • Held-out set: test cases kept aside and only used for the final measurement.
  • Working set: test cases used while tuning the agent.
  • Caller card: the details given to the AI playing the caller: a real customer's name, account number, phone, address and request.
  • Simulated caller: an AI model that plays the customer in a test conversation.
  • Reference answer: the correct answer to a test question, written in advance from the current documents.
  • Grader: an AI model that judges whether an answer matches the reference.
  • Margin of error: how far a measured percentage may be from the true value given the sample size.
  • Adversarial test: a test written to trick or break the agent.
  • Document list: the record of every knowledge-base file's status, audience, date and whether it is searchable.
  • Conflict register: the list of facts on which documents disagree, with which one wins and why.
  • Stale-trap question: a question where an excluded old document would give a different answer than the current one.
  • Embedding: a list of numbers representing a text's meaning, used to find similar text.
  • Keyword search / meaning-based search: finding passages by matching words, or by matching meaning through embeddings.
  • Recall at five / hit rate at five: the share of needed passages found in the top five results, and the share of questions with at least one needed passage in the top five.
  • Faithfulness: the share of an answer's claims supported by the passages it used.
  • Citation accuracy: whether the document an answer names contains the fact.
  • Router: the step that decides which flow a caller's message belongs to.
  • Flow: a conversation path with fixed steps and rules enforced in code, such as booking.
  • Read-only lookup: reading a caller's record without changing it.
  • Database transaction: a group of database changes that all happen together or not at all.
  • Zone: the area (north, central, south) a customer's city belongs to.
  • Members-only slot: a slot reserved for Comfort Club standard or Plus members.
  • Warranty-visit flag: a marker on an appointment meaning no diagnostic fee applies.
  • Handoff ticket: the record of an escalated conversation with everything a human needs to continue it.
  • Proof receipt: a short line after a booking or handoff showing what the system checked and did.
  • Streaming: showing a reply word by word as it is written.
  • Health endpoint: a web address the hosting service checks regularly to confirm the app is up.
  • Fly.io secrets: settings such as keys stored by the hosting service, not in the code.
  • Seeded data: the starting rows the database ships with, including the four test customers.

2. Main parts

    ENG -->|"8. events, model calls, tickets"| OPS["Operations store, alerts, jobs"]

Each message passes the numbered steps in order; the two AI models only choose a route and write wording, and code decides everything else.

  1. The browser sends each message as an ordinary request; the web layer checks that the conversation belongs to the signed visitor and opens a stream for that message's sentences.
  2. The safety check runs first on every message, even mid-flow and even for a visitor over budget; an emergency gets its fixed reply, which costs nothing.
  3. Only then are the spending and rate limits applied.
  4. With nothing in progress, a bare acknowledgement ("ok", "thanks") gets a plain "anything else?" and a goodbye ("no, that's it") ends the chat; neither is routed. The router runs on every other message. It splits a message into its requests, each with a route, a detail (such as balance, book or dispute) and a service type. With no flow active, the routes pick the flows; with a flow active, its result is used only to detect a clear change of topic, which includes a different scheduling action (booking, then cancelling another appointment).
  5. The active or chosen flows run their code-owned steps. Account and scheduling requests wait together for the caller to be identified, then run in turn; a message naming a different customer switches the conversation to that account and drops the previous customer's booking in progress. Every handoff in one message goes into one ticket. The router decides requests to act on money or membership; a code backstop catches only requests that are never questions ("send me a payment link", "set up autopay", "cancel my membership", "I want to pay my bill") on every route except a handoff (R48, D43).
  6. The flow hands the writer the facts and a reply type.
  7. Each sentence is checked before release. If a sentence fails, generation stops, the sentences already shown stay, the rest becomes a handoff message with a ticket, and a "blocked sentence" event is logged. Once the conversation has mentioned a burning smell, breaker-reset advice is blocked too.
  8. Every step records events and model calls in the operations store. One 15-second deadline covers the whole message: the router and writer calls get only the time left, and each booking change checks it just before committing, so nothing is committed after the caller has been told it was passed on.

The engine guarantees exactly one done event, always last. If the pipeline raises (for example, the operations database is unavailable, so no ticket can be saved), the engine releases a plain message asking the caller to phone the office, logs the failure to the server log and ends with an "error" done event; if the pipeline stops without a done event, it releases a plain handoff message and ends with "incomplete". A message for a conversation that belongs to another visitor gets a plain refusal ("forbidden"), and one for a closed or abandoned conversation asks the caller to start a new one.

5.1 A knowledge question

sequenceDiagram

    participant E as Conversation engine

    E->>W: 5. facts plus reply type
    W-->>G: 6. draft sentences
    G-->>B: 7. checked sentences, one by one
    E->>E: 8. log message, receipt and cost

How a fee question is answered from current documents only, with every sentence checked before it is shown.

  1. The browser sends the message as an ordinary request with its conversation id and a message id, and opens the sentence stream for that message id; the server checks the conversation belongs to the signed visitor.
  2. The safety check runs in code; nothing matches.
  3. Haiku 5.5 returns the route "knowledge" with the label "clear".
  4. Combined search returns the top five pieces; the old $79 FAQ is not in the index at all, because the document list excludes it.
  5. If the top piece's meaning-based score is below the chosen threshold, the engine goes to a handoff instead; here it is above, so the facts and a "price answer" reply type go to Sonnet 5.5.
  6. Sonnet writes the reply, which must include the source and the "technician confirms the final price on site" line.
  7. Each sentence is checked for promises, discounts, waivers and internal text, then released to the browser.
  8. The message, its receipt (route, passages, excluded stale document), its model calls and its cost are written to the operations database.

5.2 A new booking

sequenceDiagram
    participant B as Browser
    participant E as Conversation engine
    participant A as Account store
    participant P as Slot finder
    participant D as Scheduling database
    B->>E: 1. "Book a plumber, I'm Linda Foster, MHC-10001"
    E->>A: 2. identify by name plus account number
    A-->>E: customer found, north zone, standard member
    E->>P: 3. eligible plumbing slots in north zone
    P-->>E: none in three weeks
    E-->>B: 4. clean decline and ticket number
    B->>E: 5. "Then an AC repair Thursday morning"
    E->>P: 6. eligible repair slots near Thursday
    P-->>E: requested slot open
    E-->>B: 7. read back date, window, service
    B->>E: 8. "Yes"
    E->>D: 9. one transaction, only if still bookable
    D-->>E: booked, technician name
    E-->>B: 10. confirmation and proof receipt

How a booking is checked and written, including the common case where no slot exists.

  1. The caller asks to book and gives a name and account number.
  2. The account store matches name plus account number (never a name alone); after two failed attempts it would hand off.
  3. The slot finder asks for slots that are open, or members-only for standard or Plus members, in the caller's zone and service type, not yet started relative to the fixed "now", and whose technician has no overlapping booking.
  4. The north zone has no plumbing slots, so the agent says so plainly and creates a ticket naming the gap: a clean decline.
  5. The caller asks for an HVAC repair instead.
  6. The finder offers the requested slot if eligible, otherwise up to three nearest by date then window.
  7. The agent reads back the date, window and service type, with a confirmation id attached.
  8. The caller confirms. A double click or a browser retry sends the same confirmation id, which returns the first result instead of booking twice (booking, reviewer-link and downtime protections (D34)).
  9. One write-locked transaction reruns every eligibility check (slot status, zone, service, membership, not started, no overlapping booking for the technician, no other scheduled appointment on the slot), then marks the slot booked and adds the appointment row; if anything changed, the agent says the slot was just taken and offers the next three. The warranty-visit flag is set only if the install date proves the 2-year installation warranty; other warranty claims add a low-priority warranty-review ticket linked to the appointment. If the booking commits but the operations write then fails, the booking stands, the caller still gets the confirmation, the write is retried, and if it fails again the appointment id goes to the server log with an alert.
  10. The agent confirms with the technician's name and a proof receipt ("customer verified · eligibility checked · booked in one transaction").

5.3 Rescheduling or cancelling

sequenceDiagram
    participant B as Browser
    participant E as Conversation engine
    participant D as Scheduling database
    participant SC as Seed copy
    B->>E: 1. "Can I move my appointment on the 22nd?"
    E->>D: 2. find the caller's scheduled appointments
    D-->>E: one appointment, 22 Oct 08:00-12:00
    E-->>B: 3. state any 24-hour fee, offer new slots
    B->>E: 4. picks a new slot and confirms
    E->>D: 5. one transaction: recheck and book new
    D->>SC: 6. read old slot's original status
    SC-->>D: reserved_members
    D->>D: 7. move appointment and restore old slot
    D-->>E: done
    E-->>B: 8. confirmation and proof receipt

How moving an appointment keeps the database consistent and restores the old slot correctly.

  1. The identified caller asks to move an appointment.
  2. The engine reads the caller's scheduled appointments; if there are several it asks which one, reading back only date, window, service and technician.
  3. If the window starts within 24 hours of "now", the agent states the $49 fee before the caller confirms; a waiver request would hand off.
  4. The caller picks one of the offered slots and confirms.
  5. One write-locked transaction rechecks the new slot's eligibility and books it.
  6. Inside it, the old slot's status is read from the seed copy; if the seed shows it as booked (a seeded appointment), the slot is freed to open.
  7. The appointment moves and the old slot returns to its seed status (here members-only, not open). Cancelling is the same without the new booking. Both carry a confirmation id, so a repeat returns the first result; if the appointment changed after the read-back, the caller is told plainly that nothing was changed.
  8. The agent confirms with a proof receipt.

How the held-out set is measured against a fresh database copy, never the live one.

  1.   3. The caller's turns go to the same agent core the web app uses, called directly with no web layer.
  4. The agent does its lookups and booking changes on the copy.
  5. Code checks the database changes against the expected outcome.
  6. Knowledge answers go to Codex in batches of about 20 for JSON verdicts; the author is told first so Codex is set to a frontier model.
  7. The first run of each case is scored, failures are retried once and reported as flaky if they then pass, and containment is weighted by each template's call count.

Two scheduled jobs and the alerting paths; the reset waits for a lock, runs at startup if missed, and alerts after one failed retry.

  1.   3. A failed reset is retried once, then the author is alerted and the dashboard shows it.
  4. The daily purge deletes conversations older than 30 days with their messages, receipts and model calls, except conversations with a flag, which are kept until exported.
  5. 15. Trade-offs and what to revisit

  • One machine, one worker. Simple and enough for a demo; a real deployment would need a second machine and a scheduler outside the web process.
  • SQLite. Matches the provided data and keeps everything on one disk; many simultaneous writers would need a server database.
  • Index shipped in the release. Rebuilding the index means a new release, which is fine for 17 documents and makes rollback complete; a large, often-edited knowledge base would need a separate index service.
  • Sentence-by-sentence release. Safer than word-by-word streaming, at the cost of about a second before the first words appear.
  • Fixed patterns for safety. Predictable and testable, but they need the adversarial set to cover paraphrases and speech-to-text errors.

Glossary

  • Web application: the program that serves the pages and answers chat messages.
  • FastAPI: a Python framework for building web applications.
  • Worker process: one running copy of the web application handling requests.
  • Server-sent events: a way for a server to keep pushing text to a browser over one open connection.
  • SQLite: a database stored in a single file, with no separate database server.
  • Write-ahead logging: a SQLite mode that lets reads continue while a write is happening.
  • Seed copy: an untouched copy of the original scheduling database used for the nightly reset and to restore slots.
  • Operations database: the second database holding logs, tickets, costs and job records.
  • Transaction: a group of database changes that all happen together or not at all.
  • Router: the step that decides which flow a message belongs to.
  • Flow: a conversation path with fixed steps and rules enforced in code.
  • Reply type: a fixed shape for a reply (such as a price answer or a booking confirmation) that the writer must fill.
  • Reciprocal-rank fusion: a way to merge two ranked result lists by giving each item points based on its position in each list.
  • Embedding: a list of numbers representing a text's meaning, used for meaning-based search.
  • Receipt: the stored explanation of how a reply was made.
  • Ticket: the record of a handed-off conversation for staff.
  • Signed cookie: a small browser-stored value the server can verify was not altered.
  • HttpOnly, Secure, SameSite: cookie settings that hide it from page scripts, send it only over HTTPS, and limit it to this site.
  • Forged request: a request another site tricks a logged-in browser into sending; a form token blocks it.
  • Webhook: a web address the app calls to deliver a message, such as an alert.
  • Health endpoint: a web address the host checks regularly to confirm the app is alive.
  • Fly.io secret: a setting such as a key stored by the host, not in the code.
  • Disk snapshot: a saved copy of the attached disk that can be restored.
  • Release: one deployed version of the app; rolling back returns to the previous release.
  • Fixture: prepared test data added to a database copy for one test case.
  • Simulated caller: an AI playing the customer in a test conversation.
  • Template: a call pattern repeated across many transcripts with only details changed.
  • Masking: replacing phone numbers, emails and street addresses with placeholders.
  • Microdollar: one millionth of a dollar, used to add up small AI costs exactly.
  • Reset gate: a lock inside the app that every message holds briefly and the nightly reset holds alone, so they never overlap.
  • Confirmation id: a one-time id attached to a read-back so a repeated "yes" cannot book twice.
  • Uptime monitor: an outside service that regularly checks the site and alerts when it stops answering.
  • Hash: a short fingerprint of a file; if the file changes, the fingerprint changes.

Glossary

  • Action gap: calls the agent understands but deliberately hands off because they need an action it is not allowed to take
  • Agent core: the conversation logic, document search, booking and handoff, separate from the screen or phone line the caller uses
  • Agent scope: the call reasons and parts of call reasons the agent answers itself
  • Agreement rate: the share of answers where the AI grader and the human grader gave the same verdict
  • Attached disk (volume): storage that stays when the server restarts
  • Batch: a group of items sent together in one request
  • Benchmark: a fixed public test used to compare models
  • Blind label: a label given without seeing anyone else's label for the same item
  • Cached answer: an answer prepared in advance and reused so it appears instantly
  • Call driver: a reason customers call
  • Caller card: the facts given to the AI playing the caller: name, account number, phone, address and request
  • Clean decline: telling the caller plainly that no slot is available and handing off, counted as correct behaviour
  • Code-controlled flow: a conversation path whose steps and rules are enforced by program code rather than left to the AI
  • Codex: OpenAI's command-line coding agent, run here under the author's subscription
  • Cold start: the delay while a sleeping app wakes up for its first visitor
  • Conflict register: a written list of documents that disagree and which one wins, with the reason
  • Containment ceiling: the highest containment possible, equal to the share of calls about reasons the agent handles
  • Containment rate: the share of calls the AI finishes without passing them to a person
  • Correlated mistakes: errors two models make in the same way because they were built similarly, so one cannot catch the other's
  • Cut order: the agreed order in which optional work is dropped if time runs out
  • Database transaction: a group of database changes that all happen together or not at all
  • Embedding: a list of numbers representing a text's meaning, used to find similar text
  • Escalate: hand the call to a human
  • Expected outcome: the result a test case should have (contained, handed off or clean decline), fixed before tuning
  • Fail closed: when a check cannot give an answer, treat it as a failure, so the sentence is blocked rather than shown
  • Fixture: prepared test data loaded into a test copy of the database
  • Grader: a model that scores whether the agent's answer was correct
  • Ground-truth label: the label treated as correct when measuring accuracy
  • Handoff ticket: a record of an escalated call with everything a human needs to continue it
  • Hidden rules: instructions the agent follows but never reads out to the caller
  • Idempotent: safe to repeat: doing it twice has the same effect as doing it once
  • Monitoring dashboard: a screen showing how the agent is performing: calls, containment, handoffs, failures and speed
  • Observed top three: the three most common call reasons in the transcripts, whatever the agent handles
  • Per-visitor budget: a daily spending limit for one visitor, so others still have budget left
  • Priority handoff: a handoff ticket marked to be picked up first
  • Read-only lookup: reading a caller's record without changing it
  • Reciprocal-rank fusion: merging ranked lists by adding up one over (60 plus rank) for each item across the lists
  • Reference answer: the correct answer to a test question, written in advance to compare the agent against
  • Reply-speed budget: the planned time each step may take so the whole reply arrives quickly
  • Retention: how long stored data is kept before it is deleted
  • Retrieval confidence: a score for how well the best document passage matches the question
  • Rollback: returning a live system to its previous working version
  • Router: the step that decides which flow a caller's message belongs to
  • Search index: the prepared, searchable copy of the documents that the agent looks things up in
  • Seed copy: the untouched original scheduling database shipped with each release
  • Seeded data: the starting rows the database ships with, including the four test customers
  • Server-sent events: a one-way stream of text from server to browser
  • Speech-to-text / text-to-speech: turning spoken audio into written words, and written words into spoken audio
  • Suggested-question button: a clickable common question shown in the chat so the caller need not type it
  • Template family: a group of templates that are near-identical and must stay on the same side of the test split
  • Transcript template: a call pattern that repeats across many transcripts with only names, numbers and filler words changed
  • Typed event: a message with a fixed kind and fields, such as a sentence or a final summary
  • Uptime monitor: an outside service that regularly checks a site and alerts when it stops answering
  • URL fragment: the part of a web address after #, which the browser keeps to itself and never sends to the server
  • Whole-knowledge-base comparison: giving the AI every current document at once instead of searching, to show whether search earns its place
  • Write-ahead logging: a SQLite mode that lets reads continue during writes
